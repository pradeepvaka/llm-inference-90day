00

The core mental model

Performance is the interaction of work, movement, and waiting.

∴

A fast model server does not merely compute fewer operations. It keeps expensive hardware busy while moving the fewest possible bytes through the slowest parts of the system.

WORK

Arithmetic

Matrix multiplies, attention, normalization, sampling. Measured as operations or FLOPs.

MOVEMENT

Data traffic

Weights, activations, and KV cache traveling through registers, caches, HBM, PCIe, and networks.

WAITING

Latency gaps

Kernel launches, synchronization, page faults, queueing, branch divergence, and idle accelerators.

The diagnostic question

When something is slow, ask in order: Are we compute-bound, memory-bound, launch-bound, or waiting on another component?

01

C++ or Rust: owning the hot path

Python describes the operation. Native code owns the buffers, lifetimes, and tight loops.

C++

  • Direct control and a huge systems ecosystem
  • RAII ties resource release to object lifetime
  • Undefined behavior makes discipline essential
  • Common in CUDA runtimes and inference engines

Rust

  • Ownership and borrowing checked at compile time
  • No garbage collector in the request path
  • Strong concurrency safety
  • Excellent for schedulers, gateways, and control planes

Four ideas to know cold

1 · LAYOUT

Contiguous beats scattered

A flat vector lets hardware prefetchers stream cache lines. Pointer-heavy objects turn one logical walk into many dependent memory loads.

2 · LIFETIME

Allocate outside the loop

Reserve workspaces and KV pages before decode. Allocation introduces locks, metadata work, and unpredictable pauses.

3 · OWNERSHIP

One buffer, clear responsibility

Copies disappear when APIs pass views, spans, or references instead of constructing new containers.

4 · DISPATCH

Indirect work has a cost

Virtual calls, dynamic types, and tiny operators can dominate when the useful operation itself is small.

C++ · preallocate and reuse
std::vector<float> output(batch * hidden);

for (int token = 0; token < max_new_tokens; ++token) {
  // Reuse output: no heap allocation in the decode loop.
  decode_step(model, kv_cache, output.data());
  sample_next_token(output);
}
Rust · borrow the buffer
let mut output = vec![0.0_f32; batch * hidden];

for _ in 0..max_new_tokens {
    decode_step(&model, &mut kv_cache, &mut output);
    sample_next_token(&output);
}
Hot-path rule of thumb

If it executes once per request, Python may be fine. If it executes once per layer or once per token, it deserves native code, fusion, or graph capture.

02

Python performance: move the loop

The winning move is usually not “make Python faster.” It is “make Python issue less work.”

A Python loop pays for bytecode dispatch, boxed objects, reference counting, and dynamic type checks. NumPy and PyTorch accept a high-level operation, then run the loop in optimized native code. For GPU work, Python also adds kernel-launch and framework-dispatch overhead.

The optimization ladder

STEP 1

Vectorize

Replace element-by-element Python with one array or tensor operation.

STEP 2

Batch

Combine requests or tokens so every dispatch performs more useful work.

STEP 3

Fuse

Keep intermediate values in registers or shared memory instead of materializing them in HBM.

STEP 4

Capture / compile

Use graph capture or compilation to remove repeated framework and launch overhead.

Python · same reduction, different execution
import numpy as np

x = np.arange(10_000_000, dtype=np.int64)

# Slow: 10 million Python iterations
python_total = sum(int(v) for v in x)

# Fast: one Python call, native vectorized loop
numpy_total = x.sum()
Benchmark correctly

Warm up first. Use repeated runs. For GPU timing, synchronize before stopping the clock—GPU calls are asynchronous, so naive wall-clock timing measures launch time instead of execution.

03

Linux: the substrate

A serving engine is a Linux process competing for CPU time, memory pages, file descriptors, and device access.

PROCESS / THREAD

Isolation versus sharing

Processes have separate virtual address spaces. Threads share one address space, making queues and CUDA context access cheaper—but synchronization more dangerous.

VIRTUAL MEMORY

Addresses are mappings

The pointer your program sees is virtual. Page tables map it to physical memory. A missing mapping triggers a page fault; a major fault may wait on storage.

NUMA

CPU memory is not equally near

On multi-socket hosts, a CPU can access remote memory, but with lower bandwidth and higher latency. Pin workers and allocate near their NIC or GPU.

CGROUPS

Containers inherit hard limits

A pod can be throttled even when the machine looks idle. CPU quotas and memory pressure appear as latency spikes at the application level.

Memory hierarchy: the speed of distance

Capacity grows as memory moves farther from execution. Bandwidth falls, latency rises, and software must reuse data before it escapes.

These bars are conceptual, not to scale. Exact latency and bandwidth vary by architecture. What matters is the ordering and the widening gap between on-chip reuse and off-chip movement.

Worked example: one decode token

Consider an 8-billion-parameter dense model with 16-bit weights. Its weight payload is approximately 16 GB. If a single-token decode step must stream those weights once from an H100 SXM’s HBM, a simple bandwidth roof is:

time ≥ bytes moved ÷ bandwidth
≈ 16 GB ÷ 3.35 TB/s
≈ 4.8 ms/token

That implies a theoretical ceiling near 209 tokens/s before kernels, synchronization, cache effects, KV reads, and other overhead. The example uses the published peak bandwidth of the 80 GB H100 SXM; real throughput is lower.

Arithmetic intensity decides the bottleneck

Arithmetic intensity is useful operations divided by bytes moved. A kernel with low intensity hits the memory-bandwidth roof first. A kernel with high intensity can approach the compute roof.

Why batching works

With a larger batch, each fetched weight contributes to more token computations. Operations rise faster than weight traffic, arithmetic intensity increases, and the kernel can move toward the compute-bound side of the roofline.

05

CPU vs GPU execution

A CPU minimizes the time for one irregular task. A GPU maximizes the rate of many similar tasks.

CPU

  • Few sophisticated cores
  • Large caches and branch prediction
  • Excellent single-thread latency
  • Good for tokenization, scheduling, networking, sampling

GPU

  • Thousands of simpler execution lanes
  • Massive throughput under regular parallel work
  • High-bandwidth device memory
  • Good for GEMM, attention, and batched tensor operations

SIMT, without the hand-waving

CUDA organizes threads into warps of 32. A warp issues one instruction across active lanes. If lanes take different branches, the hardware executes each path while masking inactive lanes. That is divergence: the program remains correct, but parallel efficiency falls.

GRID

Whole launch

All thread blocks created for one kernel invocation.

BLOCK

Cooperating group

Threads that can synchronize and share fast on-chip memory.

WARP

Execution unit

32 threads advancing together through the same instruction stream.

Prefill and decode foreshadow Stage 3

Prefill

Many prompt tokens are processed together. Matrix multiplies are large, reuse is high, and the GPU can be compute-bound.

Decode

Each sequence advances by one token. Operations are narrow, weights are repeatedly streamed, and the GPU is often memory-bandwidth-bound.

  • Use the CPU for irregular control flow and latency-sensitive orchestration.
  • Use the GPU when work can be expressed as large, regular tensor operations.
  • Batch enough work to amortize launches and reuse weights.
  • Measure transfer time whenever data crosses PCIe or a network.

LAB 1 · PYTHON

Move the reduction loop

Compare CPython iteration with NumPy’s native loop.

20 MIN
  1. Save the script below as bench_sum.py.
  2. Run it three times; compare the medians, not one lucky result.
  3. Explain the difference without saying “NumPy is magic.”
bench_sum.py
import time
import numpy as np

x = np.arange(10_000_000, dtype=np.int64)

def timed(label, fn):
    start = time.perf_counter()
    value = fn()
    dt = time.perf_counter() - start
    print(f"{label:12s} {dt:.4f}s  result={value}")

timed("python", lambda: sum(int(v) for v in x))
timed("numpy",  lambda: x.sum())
Observe: same result, different dispatch granularity. Your exact timing depends on CPU, Python, NumPy build, and power state.
LAB 2 · MEMORY

Make cache misses visible

Walk the same array sequentially and with a large stride.

35 MIN
  1. Compile with optimization.
  2. Measure both modes with perf stat.
  3. Compare elapsed time, cache misses, and instructions.
C++ · stride.cpp
#include <chrono>
#include <iostream>
#include <vector>

int main(int argc, char** argv) {
  const size_t n = 64ull * 1024 * 1024;
  const size_t stride = argc > 1 ? 1024 : 1;
  std::vector<int> a(n, 1);
  volatile long long sum = 0;
  auto t0 = std::chrono::steady_clock::now();
  for (size_t offset = 0; offset < stride; ++offset)
    for (size_t i = offset; i < n; i += stride) sum += a[i];
  auto dt = std::chrono::duration<double>(
      std::chrono::steady_clock::now() - t0).count();
  std::cout << sum << " " << dt << "s\n";
}
Build + measure
g++ -O3 -std=c++17 stride.cpp -o stride
perf stat -e cycles,instructions,cache-references,cache-misses ./stride
perf stat -e cycles,instructions,cache-references,cache-misses ./stride strided
Observe: both runs touch every element. The order changes locality, prefetch effectiveness, and memory-level parallelism.

Below the ridge point, bandwidth is the tighter roof. Above it, compute is the tighter roof.

LAB 4 · GPU TIMING

Catch asynchronous timing

See why a CUDA call can appear impossibly fast.

20 MIN
PyTorch · synchronize before timing
import time, torch

x = torch.randn(4096, 4096, device="cuda", dtype=torch.float16)
for _ in range(10):
    _ = x @ x                       # warm-up

torch.cuda.synchronize()
start = time.perf_counter()
for _ in range(20):
    y = x @ x
torch.cuda.synchronize()
elapsed = time.perf_counter() - start
print(f"{elapsed / 20 * 1000:.3f} ms/matmul")
Observe: remove both synchronizations and the number mostly measures how quickly Python enqueues work.
