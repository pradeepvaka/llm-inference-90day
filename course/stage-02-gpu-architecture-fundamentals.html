A useful GPU mental model

A GPU is a throughput machine: many lightweight threads execute the same instruction stream over different data. Performance comes from exposing enough parallel work and keeping expensive data movement amortized.

Unit of residency
Block

A block lands on one streaming multiprocessor (SM) and stays there until completion. Its threads can cooperate through shared memory and barriers.

Unit of execution
Warp

The scheduler issues work for a warp of 32 threads. Branch divergence serializes paths taken by different lanes.

Unit of scale
SM

Each SM contains schedulers, registers, caches/shared memory, and several execution pipelines. A GPU has many SMs.

LLM inference translation: a framework launches many kernels—matrix multiplies, attention, normalization, sampling. End-to-end speed depends on kernel mix, launch overhead, synchronization, data layout, and movement between memory levels—not one headline TFLOPS number.

SIMT, not “32 CPUs”

Threads have their own registers and IDs, but a warp shares instruction issue. If half the warp takes an if branch and half takes else, the warp may execute both paths with inactive lanes masked.

Tensor cores need feeding

Peak tensor throughput assumes dense, well-shaped tile work and a data path that can sustain it. Small batches, skinny matrices, dequantization, or repeated VRAM reads can leave tensor cores waiting.

Matrix work ≈ 2 × M × N × K floating-point operations

The factor of two counts one multiply and one add. Hardware metrics may count fused multiply-add as two operations, so match the convention when comparing achieved and peak throughput.

Capacity budget

What occupies VRAM?

  • Model weights and quantization metadata
  • KV cache, growing with active tokens and sequences
  • Temporary activations and attention workspaces
  • CUDA context, kernels, graph captures, communication buffers
  • Allocator-reserved memory and fragmentation
Traffic budget

What crosses memory?

  • Weights reread when they do not remain in cache
  • KV pages read and appended during decode
  • Intermediate tensors between unfused kernels
  • Collectives over NVLink / PCIe / network in multi-GPU runs
  • Host-to-device inputs and device-to-host outputs
Ideal bandwidth time = bytes transferred ÷ sustained bandwidth

Example: moving 60 GB through a path sustaining 2.4 TB/s has a lower bound of 25 ms. That is not the application latency—launch, compute, cache behavior, synchronization, and competing traffic add to it.

Roofline shortcut: arithmetic intensity = operations ÷ bytes moved. A kernel with intensity below the machine’s peak-FLOPS/peak-bandwidth ratio is likely bandwidth-limited; above it, compute may dominate. Use sustained measurements, not only spec-sheet peaks.

04

SM occupancy without folklore

Occupancy is the ratio of resident warps to the architecture’s maximum resident warps per SM. It describes available concurrency—not useful work, tensor-core activity, or achieved performance.

Theoretical occupancy = active warps per SM ÷ maximum warps per SM

Simplified calculator

This teaching model considers only threads and blocks. Real occupancy can be lower due to registers, shared memory, architectural block limits, and compiler allocation granularity.

Thread-limited estimate
100%

8 blocks × 8 warps = 64 active warps per SM.

What limits residency?

  • Threads per block
  • Registers used per thread
  • Shared memory used per block
  • Maximum blocks and warps supported per SM
  • Register/shared-memory allocation granularity

Why 100% is not the goal

  • A compute-bound kernel may already saturate pipelines
  • Extra occupancy cannot fix serial dependencies
  • Reducing registers can introduce spills to local memory
  • Larger tiles may use more resources but improve reuse
  • Best performance is empirical, not a percentage target
Do not confuse: occupancy is resident warp capacity; GPU utilization from nvidia-smi is the sampled fraction of time one or more kernels were executing; SM throughput/utilization is a profiler metric describing pipeline activity. These are related, not interchangeable.
05

nvidia-smi: the fast triage layer

nvidia-smi is excellent for fleet health and coarse process telemetry. It is not a kernel profiler. Use it to form a hypothesis, then move to Nsight Systems or Nsight Compute when you need causality.

Snapshot

nvidia-smi

See driver/runtime compatibility, temperature, power, aggregate utilization, memory allocation, and active processes.

Machine-readable loop

nvidia-smi --query-gpu=timestamp,index,name,utilization.gpu,utilization.memory,memory.used,memory.total,power.draw,clocks.sm,temperature.gpu --format=csv -l 1

Collect one-second samples you can diff or chart. Keep units in CSV unless a parser requires otherwise.

Device monitor

nvidia-smi dmon -s pucvmet

Stream power, utilization, clocks, violations, memory, ECC, and thermal groups when supported.

Process monitor

nvidia-smi pmon -s um -c 20

Sample per-process utilization and memory. Available fields vary by device, driver, and platform.

Read the common fields correctly

GPU-Util
Percentage of the recent sample interval during which one or more kernels executed. It does not say how full the SM pipelines were.
Memory-Usage
Allocated device memory, not current memory bandwidth and not necessarily live tensors. Framework allocators often reserve pools.
Memory-Util
Recent time with device-memory read/write activity, where supported. It is not bytes/sec and can hide transaction efficiency.
Power
Board power draw versus limit. Reaching the limit alongside reduced clocks can indicate power throttling.
Perf / clocks
Performance state and current clocks. Interpret with workload phase, thermal state, and power policy.
Temp
Device temperature. High temperature is only meaningful with clock/throttle evidence and the device’s limits.
MIG
Multi-Instance GPU partitioning state. A process may see a partition rather than the full physical GPU.

Suspect CPU scheduling, launch overhead, synchronization, data loading, or too little batch work. Confirm with a timeline.

High util, low throughput

Could be bandwidth-bound, inefficient kernels, throttling, contention, or simply heavy work. Utilization alone cannot choose.

Pattern

Suspect fragmentation, another process, peak workspace, graph capture, or a mismatch between allocator and driver views.

Sampling warning: a one-second poll can miss millisecond-scale kernels and bursty gaps. Match sampling resolution to the phenomenon, and align GPU traces with request timestamps.

Hands-on lab: prove the bottleneck

Use any CUDA-capable machine with permission to profile. The lab works with a small PyTorch script or an existing inference service. Record the exact GPU, driver, framework, dtype, tensor shapes, and batch size.

A

Baseline the device

nvidia-smi --query-gpu=index,name,driver_version,memory.total,power.limit --format=csv
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv
  • Confirm the intended GPU is visible.
  • Identify competing processes before interpreting results.
  • Save the output beside your benchmark metadata.
B

Create two contrasting workloads

Run a large matrix multiply and a repeated elementwise operation over a large tensor. Warm up first, synchronize around timing, and repeat enough times to characterize variance.

# Pseudocode — adapt sizes to fit your device safely
for _ in range(warmup): matmul(A, B)
synchronize()
start = timer()
for _ in range(iters): matmul(A, B)
synchronize()
elapsed = timer() - start
  • Predict which workload should use tensor cores.
  • Predict which should show stronger memory pressure.
  • Do not allocate tensors so large that the desktop or shared machine becomes unstable.
C

Observe at service and device levels

nvidia-smi --query-gpu=timestamp,utilization.gpu,utilization.memory,memory.used,power.draw,clocks.sm --format=csv -l 1
  • Capture request latency/throughput at the same time.
  • Explain any mismatch between GPU-Util and service throughput.
  • Repeat with a larger batch or tensor dimension; change only one variable.
D

Test an occupancy hypothesis

If you have a custom CUDA kernel, compare resource usage and achieved occupancy across block sizes. If you do not, use profiler-reported launch configuration on a framework kernel and explain why you cannot tune it directly.

Record threads/block, registers/thread, shared memory/block.
Compute the likely residency limit from each resource.
Compare theoretical occupancy with achieved occupancy and throughput.
Reject any change that raises occupancy but slows the kernel.

Knowledge check

1. Why can GPU-Util be 100% while a kernel uses only a fraction of peak FLOPS?

GPU-Util says that at least one kernel was active during the sampling interval. The active kernel may be bandwidth-bound, dependency-bound, poorly vectorized, too small, or using non-tensor pipelines. It does not quantify pipeline saturation.

2. Why can lowering register use make a kernel slower?

It may increase theoretical occupancy but force values to spill into local memory, add instructions, or prevent a more efficient tile. More resident warps do not guarantee more useful throughput.

3. Why is decode often more bandwidth-sensitive than prefill?

Decode commonly performs small matrix-vector-like work per sequence while rereading weights and accessing KV state. Prefill has more tokens in parallel and often offers better matrix reuse and tensor-core efficiency.

4. Does 40 GB “memory used” mean 40 GB was read this second?

No. It is allocated or reserved capacity. Traffic requires bandwidth counters or profiler metrics; allocation can remain constant while traffic varies widely.

5. What should you do after nvidia-smi shows low utilization?

Correlate with service metrics, then inspect a timeline for CPU gaps, data copies, synchronization, communication, or tiny kernels. Low utilization identifies unused time, not its cause.
