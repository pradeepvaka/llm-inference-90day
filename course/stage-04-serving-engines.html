01 — PATH

From HTTP request to streamed token

The engine is a control plane wrapped around a repeated model forward pass. Most production failures happen in the boundaries between these boxes.

01 / ROUTERAuthenticate, rate-limit, choose replica, keep stream open.
02 / FRONTENDValidate generation parameters; tokenize and apply chat template.
03 / ADMISSIONCheck queue policy, context length, token budget, and KV capacity.
04 / SCHEDULERSelect prefill chunks and active decode sequences for this iteration.
05 / EXECUTORRun model kernels, read/write paged KV, sample next tokens.
06 / STREAMDetokenize, apply stopping rules, return deltas, release blocks.
CONTROL LOOP

At every iteration boundary: retire finished requests → free or retain their cache → admit work → build a ragged batch → launch kernels → sample → repeat. The CPU scheduler must stay ahead of the GPU or it becomes the bottleneck.

Prefill and decode compete for the same GPU

Prefill ingests many prompt tokens in parallel and tends toward compute-heavy matrix multiplications. Decode advances each sequence by one token and tends toward bandwidth-heavy weight and KV reads. Mixing them improves utilization but creates interference: a large prefill can delay the next decode step.

iteration work ≈ Σ prefill chunk tokens + # active decode sequences

Three budgets, not one

  • Sequence budget: how many requests may be active.
  • Token budget: total scheduled tokens in an iteration.
  • KV budget: physical blocks available after weights and workspace.

Whichever is exhausted first becomes the admission constraint.

02 — BATCHING

The batch is a revolving door

Static batching binds requests together until the slowest finishes. Continuous batching reschedules at iteration boundaries, so finished sequences leave and queued work enters.

Head-of-line blocking

These four requests start together. A short request’s slot stays unusable until the longest request reaches its release barrier.

Failure mode: empty slots accumulate while new arrivals wait behind the batch barrier.

Iteration-level scheduling

When A finishes, E joins at the next scheduling point. F can take C’s slot later; no request-level release barrier is required.

Key property: the active batch is ragged and changes over time. Attention kernels use per-sequence metadata rather than padding every row to one length.

03 — MEMORY

PagedAttention makes KV memory fungible

Request lengths are unknown and change one token at a time. Fixed contiguous reservations either over-allocate, fragment memory, or require costly movement. Paging decouples a sequence’s logical KV positions from physical GPU blocks.

01 / LOGICAL

Append by position

Each sequence sees a logical list of KV blocks. The next token maps to a block index and offset.

02 / MAP

Resolve a block table

The runtime maps logical blocks to any free physical blocks; contiguous virtual history does not require contiguous VRAM.

03 / ATTEND

Gather through the table

The paged attention kernel follows the mapping while computing attention over the sequence’s cached history.

What paging buys

  • Allocation close to actual sequence length.
  • Cheap growth one block at a time.
  • Fast reclamation when a request finishes.
  • Shared physical blocks for common prefixes or parallel samples, with copy-on-write semantics when needed.

What paging costs

  • Block tables and allocator bookkeeping.
  • Indirection in the attention kernel.
  • Internal fragmentation in each sequence’s final block.
  • Policy complexity under pressure: recompute, swap, reject, or preempt.
Do not conflate two ideas.

PagedAttention is the kernel/data-structure design for non-contiguous KV blocks. Continuous batching is the scheduler’s iteration-level admission policy. They reinforce each other, but either concept can be discussed independently.

04 — POLICY

The scheduler decides who feels the load

A token budget is a policy surface. Spend it on fresh prompts and TTFT improves; reserve it for active decodes and inter-token latency stabilizes.

Policy tensions

DECODE-FIRST

Protects TPOT for admitted users, but sustained decode load can make queued prompts wait. Add fairness or admission control.

PREFILL-FIRST

Improves prompt admission and TTFT at light load; large prompts can interrupt decode cadence and inflate tail TPOT.

CHUNKED PREFILL

Breaks long prompts into bounded pieces that fit around decode work. It controls interference but adds more scheduling rounds.

PRESSURE / 01

Recompute

Drop a preempted request’s KV state and rebuild it later. Saves device memory; pays future prefill compute.

PRESSURE / 02

Swap / offload

Move state to slower memory. Preserves compute; introduces transfer latency and bandwidth contention.

PRESSURE / 03

Reject / shed

Protect existing SLOs by refusing new work or routing elsewhere. Often better than unbounded queueing.

Fairness is workload-specific

FCFS is understandable but allows long prompts to create convoys. Shortest-job policies need an estimate of work and can starve large jobs. Priorities help interactive traffic but need quotas and aging. Prefix-aware routing raises cache hits but may imbalance replicas. There is no universal winner: define service classes, queue caps, cancellation behavior, and starvation bounds explicitly.

Open-loop vs closed-loop load

Closed loop waits for a response before sending more and can hide overload by self-throttling. Open loop sends at a target arrival rate, exposing queue growth and the saturation knee. Use both, but name which one produced the graph.

Capacity from the workload

request rate ≈ output token throughput ÷ mean output tokens/request

This is only a first-order conversion. Prompt cost, variance, cache reuse, batching, and SLO misses determine usable capacity.

Start with vLLM when…

You want a widely adopted general serving baseline, broad model support, standard APIs, and a clear PagedAttention mental model.

Test SGLang when…

Your traffic repeatedly shares system prompts, tool schemas, few-shot examples, or conversation prefixes—or structured programs are central.

Keep TGI when…

You operate an existing stable deployment and migration risk exceeds short-term benefit. For new deployments, follow Hugging Face’s current guidance and evaluate alternatives.

Selection rule.

First eliminate engines that cannot run the exact model/precision/hardware/API you need. Then benchmark survivors with the same workload trace and SLO. Never transplant a vendor or project benchmark into a capacity plan.

09 — DEFEND

Ship only what you can explain

A production serving choice is not “the benchmark winner.” It is a queueing policy, memory plan, failure model, and rollback strategy.

Whiteboard defense

  • Draw the request lifecycle and name every queue.
  • Derive KV bytes per token from model dimensions and dtype.
  • Explain why non-contiguous blocks reduce reservation waste.
  • State the admission rule when KV capacity is exhausted.
  • Explain prefill/decode interference and your fairness bound.
  • Define TTFT, TPOT, throughput, and goodput SLOs.
  • Show an open-loop load curve through saturation.
  • Describe cancellation, timeout, worker crash, and OOM behavior.
  • Name the pinned version, rollback trigger, and fallback engine.

Failure drills

One client disconnects mid-generation
How quickly are scheduler state and KV blocks reclaimed? Can cancellation race with a GPU iteration?
A 100K-token prompt arrives
Does it monopolize prefill, get chunked, enter a separate class, or get rejected?
Prefix-aware routing creates a hot replica
When does cache affinity lose to queue length? What is the spillover rule?
Traffic exceeds capacity for ten minutes
Which class is shed first? How are retries prevented from amplifying the overload?
