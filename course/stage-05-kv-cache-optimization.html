Stage 5 · Memory is the scheduler

KV Cache Optimization

The cache turns autoregressive decoding from “recompute the whole past” into “read the past once.” It also becomes the dominant dynamic memory consumer. This stage is about controlling that trade: reuse what is identical, schedule what is long, compress what is cold, and spill only when bandwidth permits.

01 · Mental model

The cache is a time–memory exchange.

At layer ℓ, every processed token contributes one key vector and one value vector. During decode, the new query attends over those stored vectors instead of regenerating them. Compute saved grows with history length; memory consumed grows linearly with it.

bytes / token
= 2 × L × Hkv × dhead × bytes(dtype)
2 TENSORSOne K and one V per layer. GQA MATTERSUse KV heads, not query heads. LINEAR GROWTHMultiply by live tokens and sequences.
A

Shape before layout

Conceptually: [layers, 2, kv_heads, tokens, head_dim]. Engines reorder dimensions and block tokens for kernel-friendly access.

B

Allocation before arithmetic

Logical capacity is not physical capacity. Contiguous buffers add reservation and fragmentation; block managers bound waste to the final partial block.

C

Bandwidth before capacity

A cache that fits may still be slow. Decode repeatedly streams K/V for the growing context, so dtype and memory tier affect latency as well as concurrency.

Whiteboard test: if a model uses 32 layers, 8 KV heads, head dimension 128, and BF16, each token consumes 2 × 32 × 8 × 128 × 2 = 131,072 bytes of KV cache — exactly 128 KiB before allocator metadata.

03 · The five levers

Optimize reuse first. Compress second. Spill last.

These mechanisms solve different problems. Combining them without understanding their boundaries can save memory while making latency or correctness worse.

01

Prefix caching

Reuse K/V blocks when requests begin with the same exact token prefix. It removes duplicate prefill compute and duplicate cache storage for shared blocks.

COMPUTE + MEMORY
Block identity
request Ah₀h₁h₂A₃A₄
request Bh₀h₁h₂B₃—
shared, reference-countedprivate after divergence

A common design hashes parent_hash + block_tokens + cache_identity. The parent hash makes block identity position- and history-sensitive.

Correctness boundary
  • Exact tokens: semantically equivalent text with different tokenization is a miss.
  • Exact model state: model revision, adapter/LoRA, RoPE configuration, multimodal inputs, and relevant sampling-side transforms belong in the identity.
  • Tenant isolation: salt or namespace hashes where cache existence could leak sensitive prompt reuse.
  • Whole blocks: only a complete block is typically reusable; the tail stays request-owned.
02

Decode requests consume little compute per sequence but are latency-sensitive. Remaining token budget is filled with prefill chunks, mixing memory-bound decode with compute-bound prefill.

Tune the token budget

Smaller chunks improve fairness and inter-token latency, but add scheduling and kernel-launch overhead. Larger chunks improve prefill efficiency and first-token latency for the long request, but create burstier interference.

Measure p95/p99 TTFT and ITL separately. An average can hide a scheduler that is excellent for throughput and poor for interactive tails.

03

KV quantization

Store cached keys and values in fewer bits, then dequantize or consume them directly in the attention path. Capacity scales nearly linearly with bit width; quality and kernel cost do not.

Implementation questions
  • Per-tensor, per-head, per-channel, or per-token scales?
  • Static calibration or dynamic scale computation?
  • Are K and V quantized symmetrically? Their outlier structure can differ.
  • Does the attention kernel read the compressed layout directly, or materialize a wider temporary?
  • Did long-context perplexity, retrieval, and generation regressions stay inside the product’s tolerance?
04

Cache offloading

Extend capacity by moving colder KV blocks to host memory—or, in specialized designs, local storage—and restoring them before use.

CAPACITY TIERING
Tiered pool
GPU HBMactive decode blocksFAST / SCARCE
CPU pinnedpaused or lower-priority sessionsSLOWER / LARGER
NVMespecialized long-lived cold cacheLAST RESORT
The bandwidth inequality

restore_bytes / link_bandwidth ≤ latency_slack

If the cache restore cannot finish inside the scheduler’s slack, offload converts an OOM into a latency spike. Use pinned host buffers, asynchronous copies, overlap, and a policy that predicts reuse—not only recency.

Compare against recompute: for short prefixes or congested interconnects, recomputing KV may be cheaper than transferring it back.

05

Multi-turn reuse

A conversation is an append-only sequence until it is not. Preserve the validated prefix and prefill only newly appended tokens.

SESSION REUSE
Fast path

cached_history ⧺ new_user_turn ⧺ assistant_prefix

The cache remains valid when the rendered token sequence is identical and new tokens only append. A block table can reference old pages and allocate new pages for the suffix.

Invalidate when
  • The system prompt, tool schema, model revision, or adapter changes.
  • History is edited, summarized, re-templated, or truncated before the cached tail.
  • Position encoding or attention-window semantics change.
  • A session crosses an isolation boundary.

Keep a token-level longest-common-prefix fallback. “Same conversation ID” is not sufficient cache identity.

04 · Architecture

A defensible cache manager.

Separate logical identity from physical placement. That makes reuse, paging, eviction, offload, and observability composable instead of entangled.

1 · TOKENIZEcanonical template and exact token IDs
2 · HASHparent hash + block + model identity
3 · LOOK UPlongest valid run of resident blocks
4 · SCHEDULEdecode first; chunk suffix prefill
5 · PLACEallocate, reference, evict, or restore
HIGH SHARED-PREFIX RATE

Prioritize prefix caching

  • Stable system prompts
  • Few prompt templates
  • Strong tenant boundaries
LONG PROMPTS + CHAT

Prioritize chunking

  • TTFT and ITL have separate SLOs
  • Mixed prefill/decode queue
  • Tail fairness matters
HBM-LIMITED CONCURRENCY

Quantize, then tier

  • Measure quality first
  • Verify kernel support
  • Offload only with bandwidth budget
Eviction policy is a workload hypothesis. LRU assumes recent prefixes return. Cost-aware eviction also considers block size, recompute cost, restore cost, prefix fan-out, and tenant quota. Instrument the hypothesis before making it clever.
05 · Hands-on lab

Build a block-hash cache simulator.

The lab is intentionally small: implement the identity and lifecycle rules without a GPU, then use traces to reason about what a production engine must do atomically.

kv_cache_sim.py · skeleton
from dataclasses import dataclass
from hashlib import sha256

@dataclass(frozen=True)
class Identity:
  model_rev: str
  adapter_id: str | None
  tenant_salt: bytes

def block_hash(parent: bytes, tokens: tuple[int, ...], ident: Identity):
  h = sha256()
  for part in (parent, repr(tokens).encode(),
               ident.model_rev.encode(),
               repr(ident.adapter_id).encode(), ident.tenant_salt):
    h.update(len(part).to_bytes(4, "big"))
    h.update(part)
  return h.digest()

06 · Production gates

Optimize against an SLO, not a demo.

Cache hit rate alone can rise while user latency worsens. Track the mechanism, the resource it consumes, and the outcome it is meant to improve.

REUSE
Prefix hit tokens

Count tokens skipped, not only requests with any hit. A one-block hit and a 16K-token hit are not equivalent.

LATENCY
TTFT + ITL tails

Split by prompt/output length and cache-hit status. Report p50, p95, and p99.

MEMORY
HBM occupancy

Useful bytes, reserved blocks, partial-block waste, evictions, restores, and preemptions.

QUALITY
Quantization delta

Long-context retrieval, task accuracy, perplexity proxy, and output agreement versus baseline.

GATE 1 · CORRECT

Exact-match outputs against the unoptimized path where the optimization is intended to be lossless; explicit quality tolerance where quantization is lossy.

GATE 2 · ISOLATED

No cross-model, cross-adapter, or cross-tenant reuse. Cache keys and metrics must not expose sensitive prompt content.

GATE 3 · FASTER

Representative load test shows the targeted SLO improves without unacceptable regression elsewhere. Include cold-cache and warm-cache runs.

GATE 4 · STABLE

No refcount leaks, stale block-table entries, eviction races, or transfer storms under cancellation, preemption, and overload.

07 · Knowledge check

Can you defend the design?

Open each answer only after you can explain it aloud.

Multiple query heads share each key/value head. The cache stores K and V for KV heads, while query projections can still have more heads. The attention kernel maps groups of query heads to a shared KV head.
The same token block can appear after different histories. Its K/V depends on prior context and position, so block tokens alone are not a valid identity. Chaining the parent commits to the entire prefix.
Chunks that are too small add scheduling and launch overhead and delay the long request’s first token. Poor policies can also over-prioritize decode, starving prefills. Tune against both TTFT and ITL distributions.
Restoring a large KV region over a constrained link can exceed the cost of rerunning prefill, especially for shorter prefixes or when transfer cannot overlap with useful work. Compare bytes/bandwidth with measured recompute time.
History can be edited, summarized, truncated, re-templated, or served by another model/adapter while retaining the same ID. Cache validity depends on the exact token prefix plus model state, not a logical session label.
