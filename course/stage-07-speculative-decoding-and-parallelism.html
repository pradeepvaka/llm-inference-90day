01 / THE LATENCY WALL

Autoregression serializes the scarce operation.

With a KV cache, each decode step computes one new position—but still streams a large fraction of model weights through the accelerator. At low batch size, that pass is often memory-bandwidth-bound rather than FLOP-bound.

Serial dependency

Token xₜ₊₁ depends on the sampled xₜ. Vanilla decoding therefore needs one target-model call per emitted token.

Unused arithmetic

Scoring several known positions together has more parallel work than scoring one. Verification can use compute that single-token decode leaves idle.

Distribution matters

“Predict K tokens at once” is not enough. A production method must either preserve the target sampler exactly or declare a quality-changing approximation.

vanilla decode latency
T ≈ N · ttarget,1

goal: amortize a target pass over more than one accepted token
effective latency/token ≈ (draft work + verify work) / accepted output tokens
!
First diagnosis: latency-bound or throughput-bound?

Speculation usually targets low-batch inter-token latency. Under heavy continuous batching, verification consumes extra token slots and can reduce total goodput. Measure both time-to-first-token and inter-token latency, but optimize against the service objective that actually matters.

02 / DRAFT → VERIFY

A cheap model guesses; the target settles the account.

Let a draft distribution q propose γ tokens. One target forward pass evaluates those positions under p. Accept the longest valid prefix, repair the first rejection, and repeat.

01Draft

Sample γ tokens autoregressively from the cheap model q.

02Score

Run the target once over the proposed extension.

03Compare

At each position inspect p(x) and q(x).

04Accept

Keep tokens left-to-right while the acceptance test passes.

05Repair

At first rejection, sample from the residual distribution.

06Advance

If all pass, sample one bonus token from the target.

Exact sampling, not “draft agrees with argmax”

a(x) = min(1, p(x) / q(x))
accept proposed token x with probability a(x)

presidual(x) ∝ max(0, p(x) − q(x))
on rejection, sample the correction from normalized positive residual

The draft is trusted only for probability mass that the target also assigns. The residual correction restores mass where the target exceeds the draft. Together, accepted proposals plus corrected rejections reproduce the target distribution. Apply the same temperature and truncation policy consistently when computing the two distributions.

What the toy model leaves out

Correlation

Acceptance events are not independent: one disagreement changes the prefix and invalidates later proposals.

Scheduler

Variable accepted lengths complicate batching, cache allocation, and fairness across requests.

Kernel shape

A γ-position verify pass is not exactly one decode step; attention, sampling, and launch overheads change.

Heads are not independent autoregressive futures.

05 / COMPOSITION

The techniques multiply—and interfere.

A production serving stack may combine replica-level data parallelism, tensor shards, pipeline stages, KV-cache paging, quantization, and speculative verification. Each optimization changes the operating point of the others.

TRAFFICReplicas

Route requests across model instances. Autoscale on goodput and tail latency, not raw GPU utilization.

PLACEMENTTP × PP mesh

Fit target weights while respecting fast-link domains and stage balance.

EXECUTIONContinuous batches

Co-schedule prefill, decode, verification, and variable-length acceptance.

DECODINGDraft or heads

Propose candidate tokens only when expected accepted work beats its opportunity cost.

Cross-effects to reason about

Speculation × TP

The target verify pass scores more positions per collective sequence. That can improve compute/communication amortization—but a draft model spanning ranks may erase the win.

Speculation × PP

Verification blocks are wider, yet accepted lengths vary. The scheduler must avoid turning one request’s long tree into bubbles or head-of-line blocking.

Quantization × draft

A quantized draft can be cheaper, but its changed probabilities may lower acceptance. Optimize end-to-end accepted tokens per second, not draft tokens per second.

KV cache × candidates

Draft KV, candidate tokens, and tree verification all consume memory. Budget this before raising batch size or speculative width.

SLO
Use an admission policy, not a global on/off switch.

Short outputs, high temperature, overloaded batches, or weak draft agreement may not benefit. Route speculation by request class and current scheduler pressure, with a plain target-only fallback.

06 / HANDS-ON LAB

Build the acceptance loop before the kernels.

This is a PoC: use tiny categorical distributions to validate correctness and intuition. Do not optimize kernels until the probability path and instrumentation are defensible.

speculative_step.py · framework-neutral pseudocode
def speculative_step(prefix, gamma, draft, target, rng):
    proposed, q_probs = [], []

    for _ in range(gamma):
        q = apply_sampling_policy(draft.next(prefix + proposed))
        x = rng.categorical(q)
        proposed.append(x)
        q_probs.append(q)

    # One target call returns distributions for every proposed position.
    p_probs = target.score_extension(prefix, proposed)
    accepted = []

    for x, p, q in zip(proposed, p_probs, q_probs):
        ratio = min(1.0, p[x] / max(q[x], EPS))
        if rng.uniform() <= ratio:
            accepted.append(x)
        else:
            residual = normalize(max_elementwise(p - q, 0.0))
            accepted.append(rng.categorical(residual))
            return accepted

    # All proposals survived: emit one target-only bonus token.
    accepted.append(rng.categorical(p_probs.bonus))
    return accepted

Prove the sampler first

Use a vocabulary of 4–8 symbols and fixed p/q. Draw at least 100k outputs from target-only and speculative paths; compare empirical frequencies and confidence intervals.

Sweep disagreement

Interpolate q = λp + (1−λ)r. Plot acceptance, expected emitted tokens per target call, and wall-clock proxy as λ changes.

Add a real tiny model pair

Use models with the same tokenizer. Record draft latency, verify latency by γ, accepted prefix length, draft KV bytes, and target-only baseline.

Stress the scheduler

Mix prompt lengths, output lengths, and temperatures. Measure goodput at fixed P95/P99 inter-token SLO instead of reporting isolated batch-1 speedup.

Defend the design

Explain the rejection rule, adversarial low-acceptance behavior, cache ownership, cancellation path, failure fallback, and why the chosen TP/PP placement matches the fabric.

Exit criteria

  • distribution test passes in exact mode
  • break-even region measured, not assumed
  • target-only fallback tested
  • tail latency and goodput reported together

Common implementation bugs

  • sampling p and q with different filters
  • keeping tokens after the first rejection
  • renormalizing the residual incorrectly
  • reusing candidate KV state after repair
07 / CHECKPOINT

Can you defend the system?

Answer before revealing. A strong answer names the mechanism, the resource tradeoff, and the failure mode.

Because the proposals make the whole candidate prefix known. A causal transformer can score every proposed position in parallel within one forward pass, while its mask still prevents each position from attending to future candidate tokens.
Argmax matching discards the target’s sampling distribution. Exact sampling accepts with min(1,p/q) and, on rejection, samples from the normalized positive residual (p−q)₊, preserving the target distribution under the same sampling policy.
If the accuracy gain costs too much latency, HBM, KV memory, synchronization, or scheduler capacity. Acceptance rate is only one term; end-to-end goodput and tail latency decide whether the pair is better.
TP performs frequent collectives inside transformer blocks. Those synchronizations are sensitive to latency and bandwidth, so fast accelerator interconnects are far better than crossing a slower network fabric.
A token still traverses the pipeline stages serially. PP improves memory capacity and can improve aggregate throughput when many microbatches or sequences keep stages busy, but fill/drain bubbles and stage hops remain.
