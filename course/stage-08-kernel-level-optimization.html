01 · Mental model

Two floors of the machine

A kernel's runtime is decided by a contract between two numbers: how many bytes it must move, and how many times it makes the CPU launch it. Every technique in this stage attacks one of those two numbers.

The floors a byte climbsH100 SXM, advertised figures
Registers255/thread · 64K regs/SM~1 cycle latency · the true working set
Shared / L1 SRAM228 KB per block opt-insingle-digit cycles · where tiling happens
L2 cache60 MB, ~4× A100tens of cycles · shared across all SMs
HBM380 GB · ≈3.35 TB/shundreds of cycles · the fuel bill for decode
Host / peersPCIe ≈64 GB/s · NVLink 900 GB/sµs to ms · a failure if touched per step

A decode step that re-reads 14 GB of weights per token at 3.35 TB/s cannot go faster than ~4.2 ms/token no matter how many tensor cores sit idle. Up and down these floors, every hop costs latency and picojoules.

⌁

Bound 1: bytes moved

The roofline limit: at arithmetic intensity AI (FLOP/byte), no kernel exceeds min(peak FLOPS, AI × memory BW). Decode GEMMs and norms run at AI ≈ 0.25–2 FLOP/byte — they are pinned to memory bandwidth. The only levers: fewer passes over the data (fusion), fewer bytes per element (quantization), and doing work once in SRAM (tiling).

◷

Bound 2: launches issued

Each kernel launch costs ≈3–10 µs of CPU-side overhead plus synchronization. A 70B decoder step can issue 50–200 launches; a large fraction of small-kernel decode time is pure launcher tax. CUDA graphs capture the DAG once and replay it with one CPU call; persistent kernels go further and never return to the host at all.

Whiteboard defense ready. When someone proposes a kernel optimization, the two questions are: how many bytes does it move per output element? and how many launches per decode step? Everything else — occupancy, bank conflicts, instruction pipelines — is a second-order term until these two are accounted for. Run them through the roofline and launch-overhead labs below before believing any claim.

The optimization taxonomy

02 · Triton kernels

Blocks, not threads

Triton is a Python-embedded language that compiles to GPU code via MLIR. Its core abstraction shift: you program one program instance per thread block, operating on blocks of data, not threads of data. The compiler handles warp scheduling, coalescing, and tensor-core instruction selection.

The mental model: grid → program → tensors

A @triton.jit function runs once per program ID in a grid (a grid dimension ~ thread blocks). Inside, every tl.arange builds an index tensor — one logical element per output lane. Loads/stores move blocks, tl.dot maps to tensor cores when shapes qualify, and a mask argument handles ragged edges so you never branch on thread IDs.

import torch, triton
import triton.language as tl

@triton.jit
def _rmsnorm_fwd(x_ptr, y_ptr, w_ptr, rstd_ptr,
                 stride, N: tl.constexpr, eps: tl.constexpr,
                 BLOCK: tl.constexpr):
    row = tl.program_id(0)                       # one program per row
    x_ptr += row * stride
    y_ptr += row * stride
    cols = tl.arange(0, BLOCK)

    # Pass 1: variance over a grid-strided loop, masked at the edge
    acc = 0.0
    for off in range(0, N, BLOCK):
        idx = off + cols
        x = tl.load(x_ptr + idx, mask=idx < N, other=0.0).to(tl.float32)
        acc += tl.sum(x * x, axis=0)
    rstd = 1.0 / tl.sqrt(acc / N + eps)
    tl.store(rstd_ptr + row, rstd)

    # Pass 2: normalize + scale, fused into the same kernel
    for off in range(0, N, BLOCK):
        idx = off + cols
        x = tl.load(x_ptr + idx, mask=idx < N, other=0.0).to(tl.float32)
        w = tl.load(w_ptr + idx, mask=idx < N, other=1.0)
        tl.store(y_ptr + idx, (x * rstd * w).to(tl.float16), mask=idx < N)

def rmsnorm(x: torch.Tensor, w: torch.Tensor) -> torch.Tensor:
    M, N = x.shape
    y = torch.empty_like(x)
    rstd = torch.empty(M, dtype=torch.float32, device=x.device)
    #                          grid : one block per row
    _rmsnorm_fwd[(M,)](x, y, w, rstd, x.stride(0), N,
                       eps=1e-6, BLOCK=triton.next_power_of_2(N))
    return y

Above: one kernel replaces a torch chain of square → mean → rsqrt → mul → mul that touches HBM ~6× per element. The fused kernel touches every element exactly once per pass. It compiles — no CUDA toolkit build step; triton ships a compiler inside the wheel.

What to tune, in order of leverage

  1. Block size = how much each wave keeps in SRAM.
    Powers of two; tl.dot wants blocks ≥16 for tensor cores. Larger blocks amortize load latency but raise register pressure, which can kill occupancy (fewer blocks resident per SM).
  2. num_warps = parallelism per block.
    More warps hide memory latency but split the register file 4-ways per added warp. Memory-bound kernels saturate at low warp counts; compute-bound ones need higher warps to feed tensor cores.
  3. num_stages for pipelined loads.
    Software-pipelined loads (double/triple buffering) overlap HBM fetch with matmul. On Hopper, tl.dot with the right descriptor pattern can emit TMA + wgmma; plain pipelining gets you most of the way there.
  4. @triton.autotune over configs.
    Key the search on powers-of-two BLOCK + a few warp/stage values, prune by wall time at the sizes you serve. Autotune caches once per shape — this is the JIT tax that CUDA graphs must not capture.
When Triton wins, when it loses. Triton is the productivity answer for fusion of your own opchains and irregular reductions — rmsnorm, SwiGLU, RoPE, tree-attention variants. It does not replace hand-tuned libraries at their peak: vendor CUTLASS/cublas GEMMs and FlashAttention-3's Hopper-asynchronous kernels still beat naive tl.dot loops at large shapes. Rule of thumb: take the library kernel, fall back to Triton where no good one exists, and beat torch's eager opchain by 3–10× exactly when passes-per-element drop from many to one.

Three failure modes beginners hit

SymptomUsual causeFix
Nan/extra lanes on ragged shapesMissing mask on load/storeAlways carry mask=idx < N; mask both passes of multi-write kernels.
Slower than torch eagerSlow compile path / fp32 inside tl.dotAccumulate in fp32 (torch parity) but feed bf16/fp16 tiles so tensor cores trigger; check emitted PTX for mma ops.
Compile time explodesPython control flow over large constantsKeep range() loops small and tl.constexpr-bounded; prefer tl.multiple_of hints over dynamic shapes.
03 · FlashAttention

Tile away the N² matrix

Standard attention materializes the N×N score matrix: it writes N² scores to HBM, reads them back for softmax, writes probabilities, and reads them again for ×V — with arithmetic intensity near the FLOPs-of-nmatmul scale but traffic quadratic in N. FlashAttention keeps the scores in SRAM by tiling Q into row-blocks, streaming K/V columns, and tracking softmax statistics incrementally.

One Q-block, streaming through K/VBₘ rows of Q in SRAM; Kⱼ, Vⱼ tiles stream
Q blocked over rows (each cell = one block of rows)
S = QKᵀ never exists in HBM — only Bₘ×Bₙ tiles in SRAM
SRAM-resident this iteration stays conceptual — never written to HBM

Grid: 8 K/V column-blocks. Outer loop fixes one Q-block on SRAM; inner loop streams Kj, Vj, accumulates into O with running statistics, and the N² matrix stays conceptual. Column 1 shown consumed; column 2 in flight.

The online softmax

Softmax needs the row-max and row-sum — both global over the row. FlashAttention computes them incrementally: each iteration processes a K/V tile and rescales the accumulated output and statistics. The update per row-block i and tile j, with running max m, normalizer ℓ, accumulator O:

S⁽ʲ⁾ = Qᵢ Kⱼᵀ  ·  m̃⁽ʲ⁾ = rowmax(S⁽ʲ⁾)  ·  P̃⁽ʲ⁾ = exp(S⁽ʲ⁾ − m̃⁽ʲ⁾)  ·  ℓ̃⁽ʲ⁾ = rowsum(P̃⁽ʲ⁾)
m⁽ʲ⁾ = max(m⁽ʲ⁻¹⁾, m̃⁽ʲ⁾)
ℓ⁽ʲ⁾ = em⁽ʲ⁻¹⁾ − m⁽ʲ⁾ ℓ⁽ʲ⁻¹⁾ + em̃⁽ʲ⁾ − m⁽ʲ⁾ ℓ̃⁽ʲ⁾
O⁽ʲ⁾ = diag(em⁽ʲ⁻¹⁾ − m⁽ʲ⁾) O⁽ʲ⁻¹⁾ + em̃⁽ʲ⁾ − m⁽ʲ⁾ P̃⁽ʲ⁾ Vⱼ

This is exact attention — bitwise-equivalent up to floating-point associativity, not sparse or approximate. The asymptotics barely change (still Θ(N²d) FLOPs), but HBM traffic collapses from Θ(Nd + N²) with 3 N² trips to roughly Θ(Nd + N²d²/M) reads, where M is SRAM size. At long contexts that is the entire speedup.

SRAM budget is the config space

The kernel's feasibility and speed are decided by shared-memory usage. A faithful forward pass holds per program block Qᵢ (Bm×d), Kⱼ, Vⱼ (each Bn×d), the score tile (Bm×Bn), and the FP32 accumulator (Bm×d):

SRAM ≈ 2(Bm + 2Bn)·d + 2·Bm·Bn + 4·Bm·d bytes

On A100 the working ceiling is 164 KB (opt-in 227 KB on H100). Too large and the block can't launch; too small and tensor cores starve on skinny tiles. Use the tiling lab in §7 to explore real (block, head-dim) combinations before touching a compiler.

Three generations, one idea

VersionKey changeWhy it matters
FA-1IO-aware exact attention, tiling + online softmaxBecame the fused prefill standard; 2–4× wall-time over naive attention at long N.
FA-2Parallelize over sequence length, not just batch×heads; fewer non-matmul FLOPsBetter occupancy at short sequences and small batch — the serving regime.
FA-3Hopper warp-specialization, asynchronous TMA loads, FP8, CUTLASS-3Overlaps memory movement with tensor-core compute; often 1.5–2× over FA-2 on H100.
Decode is a different kernel. With Nquery=1, attention attention is GEMV against the KV cache: QKᵀ is a thin row-vector, S never approaches N², and FlashAttention's tiling buys little. Decode kernels (flash-decoding, split-K, paged-attention variants) instead parallelize over K/V shards and combine partial softmaxes — the same online-statistics math, applied along a different axis. Do not quote prefill FA speedups for decode workloads.
04 · CUDA graphs

Record once. Replay at launch cost ≈ 0.

A decode step is a fixed DAG of kernels: matmuls, norms, RoPE, KV writes, all-reduces. Launching them one by one costs CPU-side overhead per node — typically 3–10 µs each, dominating small-batch decode where kernels themselves run 1–20 µs. CUDA graphs let the driver replay the entire DAG with a single CPU call.

One decode step: 10 launches, 8 µs overhead eachillustrative, not measured
Eager: every launch pays CPU tax
CUDA graph: capture once, replay as one
CPU launch overhead (~8 µs each) GPU compute (kernel bodies) single replay (~3 µs)

With 10 kernels at 5 µs of compute each: eager costs 10×(8+5)=130 µs; graph replay costs 3+10×5=53 µs. The wider the decode DAG in launch count relative to compute, the bigger the win — set your own numbers in the launch lab.

Capture, then replay

# Static pools: graphs replay the same buffers, never alloc/free
static_x   = torch.empty(B_max, d, dtype=torch.bfloat16, device="cuda")
static_out = torch.empty(B_max, out_d, dtype=torch.bfloat16, device="cuda")

# Warm up kernels once, then capture the whole step
for _ in range(3):
    model.decode_step(static_x, out=static_out)

g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    model.decode_step(static_x, out=static_out)

# --- steady state: copy in, replay, read out (one CPU call) ---
static_x.copy_(next_inputs)   # memcpy stays *outside* the graph
g.replay()
use(static_out)

Rules that must hold for capture

  1. Static shapes and addresses.
    No malloc/free, no shape-dependent control flow, no re-allocating buffers mid-graph. Pad to max sizes and mask; batching systems keep a graph per bucket.
  2. No CPU-GPU synchronization.
    .item(), cuda.synchronize(), tensor printing — anything that forces the host to wait on the device breaks capture. Sampling kernels may fail this; keep them outside or use device-side RNG.
  3. No host-data-dependent branching.
    EOS checks, dynamic stop conditions, and recompute decisions live outside the graph. vLLM-style engines run the graph for the model, then handle control flow on the host per step.
  4. Autotune after, not during.
    Triton/config autotuning must settle before capture — otherwise the captured work changes when a new config wins. Warm up until kernel selection converges, then record.
Composes with torch.compile. torch.compile(model, mode="max-autotune", fullgraph=True) generates fused kernels and can wrap the region in a CUDA graph via cudagraph_trees specializations. Let Inductor do fusion and block-size search; reserve hand capture for the heterogeneous serving DAGs (decode + sampling + KV ops) that no compiler fully owns yet.
05 · Operator fusion

Count passes, not ops

Un-fused chains charge full HBM round trips per operator. A decoder layer's gated MLP alone would touch the hidden vector many times per element; fusion makes that trip once. The roofline says bytes bound decode — fusion is the most direct way to delete bytes.

SwiGLU arithmetic

A SwiGLU block computes, per element of hidden size d:

y = wout · (silu(xWgate) ⊙ xWup) + residual

Written as separate torch ops, the elementwise portion reads and writes each element several times: load gate-output, store silu, load silu + up-output, store pointwise product, load plus residual, store. Counting against an FP16 element (2 bytes) and a pass touching ≈3 tensors:

byteseager ≈ 6 reads + 5 writes per element ·  bytesfused ≈ 3 reads + 1 write per element

A conservative count of the elementwise loads/stores drops from double-digit byte traffic per element to a single blockwise pass that reads each source once and writes once. Measured consequence: fused elementwise blocks in production engines run 2–4× faster than eager chains at memory-bound hidden sizes, and every byte not moved is a microsecond the HBM never billed.

Fusion discipline. Inductor fuses automatically under torch.compile; hand-written Triton buys you fusions the compiler can't see yet (norm→quant, speculative accept paths). In both cases: profile the fused kernel's DRAM traffic with ncu --set roofline or you'll just as often discover the "fused" version spilled registers and moved more bytes. Claims are settled in bytes moved, §6.

06 · Nsight profiling

Make the GPU tell on itself

Nsight Systems gives you the timeline (which kernels, when, for how long, what overlapped). Nsight Compute gives you the inside of one kernel (where its stalls live, how close to roofline it runs). In that order, always: optimize the timeline before you tune kernels.

The canonical workflow

  1. Timeline first: nsys profile.
    Capture one representative window (steady-state decode, no warmup). Read the kernel list sorted by total time; find the gaps — empty stretches are launcher tax, CPU-bound stretches are synchronization.
  2. Annotate with NVTX ranges.
    torch.cuda.nvtx.range("decode_step") around your step, per-layer or per-op ranges inside. Timeline attribution without ranges is archaeology.
  3. One kernel deep: ncu --set roofline.
    Replay the top kernel, read achieved AI vs the ridge point, SM vs DRAM throughput, and warp stall reasons. Roofline tells you if it's compute-, L2-, or DRAM-bound.
  4. Guided analysis, then change, then measure again.
    ncu --analysis guided suggests the next metric set after the roofline. Make one change, re-run at the same batch/seq/shape. One variable at a time.
# 1. Timeline of a representative steady-state run
nsys profile -t cuda,nvtx -o decode --stats=true \
    python infer.py --iters 500 --bs 8 --seq 2048

# 2. Which kernels own the time? (text summary)
nsys stats decode.nsys-rep --report cuda_gpu_kern_sum

# 3. Roofline the hottest kernel (regex narrows it: ncu replays kernels,
#    so an unscoped profile of a full model can take hours)
ncu --export decode_kern --force-overwrite --set roofline \
    --kernel-name regex:flash_fwd \
    python infer.py --iters 50 --bs 8 --seq 2048

# 4. Guided: let ncu pick the next metrics after the roofline
ncu --export decode_guided --force-overwrite --analysis guided \
    --kernel-name regex:flash_fwd \
    python infer.py --iters 50 --bs 8 --seq 2048

nvprof is dead. CUPTI-based nvprof was deprecated years ago; current drivers only serve Nsight. Many old blog recipes still cite it — translate: nvprof --print-gpu-trace → nsys, nvprof --metrics → ncu. And never profile through MPS-shared GPUs or a warm card throttled from clocks — one lock-down run at locked clocks is worth ten flaky ones (nvidia-smi -lgc).

Lab D · Fused RMSNorm: beat eager on your box

Save as rmsnorm_lab.py and run on any CUDA GPU. It benchmarks the kernel from §2 against the eager torch chain (which this page's Triton code was written to replace) and reports the speedup plus DRAM traffic you can cross-check with ncu.

# rmsnorm_lab.py — run:  python rmsnorm_lab.py
# Requires: torch (CUDA build), triton, and a CUDA-capable GPU
import torch, triton
import triton.language as tl
import triton.testing as testing

@triton.jit
def _rmsnorm_fwd(x_ptr, y_ptr, w_ptr, rstd_ptr,
                 stride, N: tl.constexpr, eps: tl.constexpr,
                 BLOCK: tl.constexpr):
    row = tl.program_id(0)
    x_ptr += row * stride
    y_ptr += row * stride
    cols = tl.arange(0, BLOCK)
    acc = 0.0
    for off in range(0, N, BLOCK):
        idx = off + cols
        x = tl.load(x_ptr + idx, mask=idx < N, other=0.0).to(tl.float32)
        acc += tl.sum(x * x, axis=0)
    rstd = 1.0 / tl.sqrt(acc / N + eps)
    tl.store(rstd_ptr + row, rstd)
    for off in range(0, N, BLOCK):
        idx = off + cols
        x = tl.load(x_ptr + idx, mask=idx < N, other=0.0).to(tl.float32)
        w = tl.load(w_ptr + idx, mask=idx < N, other=1.0)
        tl.store(y_ptr + idx, (x * rstd * w).to(tl.float16), mask=idx < N)

def rmsnorm_triton(x, w):
    M, N = x.shape
    y = torch.empty_like(x)
    rstd = torch.empty(M, dtype=torch.float32, device=x.device)
    _rmsnorm_fwd[(M,)](x, y, w, rstd, x.stride(0), N,
                       eps=1e-6, BLOCK=triton.next_power_of_2(N))
    return y

def rmsnorm_eager(x, w):
    return x.float() * torch.rsqrt((x.float() ** 2).mean(-1, keepdim=True) + 1e-6) * w

M, N = 1024, 8192
x = torch.randn(M, N, dtype=torch.float16, device="cuda")
w = torch.randn(N, dtype=torch.float32, device="cuda")

# 1. Correctness: match torch to float precision relative tolerance
ref = rmsnorm_eager(x, w).half()
out = rmsnorm_triton(x, w)
assert torch.allclose(ref, out, atol=1e-2, rtol=1e-2), "mismatch!"
print("correctness: OK")

# 2. Benchmark, median over repeats (locks out noise)
@testing.do_bench
def bench(fn, *a):
    fn(*a)

e = bench(lambda: rmsnorm_eager(x, w))       # ms
t = bench(lambda: rmsnorm_triton(x, w))      # ms
print(f"eager:  {e:.3f} ms   triton: {t:.3f} ms   speedup: {e/t:.2f}x")

# 3. Follow-up verification with Nsight:
#    ncu --set roofline --kernel-name regex:_rmsnorm_fwd python rmsnorm_lab.py

Lab E · Graph capture of a decode-style loop

A 70-layer model is just a scaled-up version of this: a fixed op DAG over static buffers. Capture a multi-layer MLP loop, measure eager vs graph, and match the speedup to the launch-overhead model from Lab C.

# graph_lab.py — run:  python graph_lab.py
# Compares eager vs CUDA-graph replay for a 12-layer MLP "decode" loop
import torch, time

device = "cuda"
B, D = 8, 8192
LAYERS = 12

linears = [torch.nn.Linear(D, D, bias=False).to(device).bfloat16()
           for _ in range(LAYERS)]
norms = [torch.nn.LayerNorm(D).to(device).bfloat16() for _ in range(LAYERS)]

def step(x, out):
    for ln, fc in zip(linears, norms):        # fixed DAG, no control flow
        out.copy_(torch.nn.functional.silu(fc(x)) + x)
        x = out
    return out

x = torch.randn(B, D, dtype=torch.bfloat16, device=device)
out = torch.empty(B, D, dtype=torch.bfloat16, device=device)
torch.cuda.synchronize()

def timeit(fn, iters=200):
    for _ in range(20): fn()                 # warm
    torch.cuda.synchronize()
    t0 = time.perf_counter()
    for _ in range(iters): fn()
    torch.cuda.synchronize()
    return (time.perf_counter() - t0) / iters * 1e6   # µs/iter

eager_us = timeit(lambda: step(x, out))

# Capture: same buffers, same DAG, one replay = one CPU call
g = torch.cuda.CUDAGraph()
with torch.cuda.graph(g):
    step(x, out)
graph_us = timeit(lambda: g.replay())

print(f"eager: {eager_us:7.1f} µs/iter")
print(f"graph: {graph_us:7.1f} µs/iter   speedup: {eager_us / graph_us:.2f}x")
# Check with nsys: gaps between kernels should vanish in replay.
# nsys profile -t cuda --stats=true python graph_lab.py

08 · Knowledge check

Defend the design

Choose an answer, then read the explanation. A production design review for kernel work should demand this same reasoning.

1. FlashAttention runs essentially the same FLOPs as standard attention — where does its speedup come from?

FA is exact attention. Standard attention writes/reads the N² score and probability matrices between op passes; FlashAttention computes softmax on SRAM tiles with running statistics, so the N² traffic never leaves the SM.

2. Batch-1 decode of an FP16 70B-class model moves ~140 GB of weights per token and runs at ~3.35 TB/s. Which kernel-level lever cuts time-per-token most?

Batch-1 decode GEMMs sit at AI ≈ 1–2 FLOP/byte, deep on the memory-bound side of the ridge. Only moving fewer bytes — or moving them faster (HBM→SRAM) — advances the bound; extra compute and more parallelism buy nothing at fixed memory traffic.

3. A CUDA graph capture fails. Which change most likely fixes it?

Graphs forbid CPU-GPU synchronization and data-dependent control flow inside the captured DAG. A .item() forces the host to wait on a device value — that breaks capture. Control flow and allocations live outside the graph.

4. In Nsight Compute, a decode matmul shows "stall long scoreboard" dominating and DRAM pipe near 0. What is the diagnosis?

"Stall long scoreboard" = warps waiting on memory. If DRAM throughput is also low, the SM isn't keeping enough bytes in flight — the kernel launches too little work per wave (small batch, skinny tiles) to saturate the pipes. Fix shape/tiling, not the memory system.

5. Why quote FlashAttention speedups for prefill only, not decode?

FlashAttention's win is not materializing an N² intermediate. Decode has no such materialization: QKᵀ at batch-1×1 is a GEMV row-vector, so FA's tiling is nearly irrelevant; decode needs split-K / flash-decoding style parallelism over the KV axis instead.
