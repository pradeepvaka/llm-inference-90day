Queue-based scaling with KEDA

KEDA (Kubernetes Event-Driven Autoscaling) scales workloads from external signals — queue length, Prometheus metrics, Kafka lag — including scale-to-zero. For LLMs, the queue is the demand signal.

Why CPU / RPS autoscaling fails for LLMs

  • CPU is idle while GPU is saturated. HPA on CPU scales the wrong resource.
  • Requests are not equal. A 128-token chat and a 32k-context summarization differ by 100× in work.
  • Latency is non-linear. At high batch / KV-cache pressure, one extra request can push everyone past SLO.
  • Startup is slow. By the time RPS triggers a scale-up and the pod is warm, the burst may be gone — or the queue has exploded.

What to scale on instead

  • Waiting queue depth — requests waiting in vLLM / TGI / router.
  • Running + waiting relative to max_num_seqs.
  • KV-cache utilization — near-full cache = preemptions coming.
  • Tokens in queue (prompt tokens queued) — better than request count when lengths vary.
  • Time-to-first-token (TTFT) p95 as a guardrail, not the primary trigger — it's lagging.

A production-shaped KEDA ScaledObject (vLLM on Prometheus)

# Scale on queue depth exposed by vLLM's /metrics endpoint
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: { name: llm-inference }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: vllm }
  minReplicaCount: 1      # 0 = scale-to-zero; keep 1 if cold start > SLO allows
  maxReplicaCount: 12
  pollingInterval: 15     # seconds — faster polling ≠ faster GPUs
  cooldownPeriod: 300     # 5 min: avoid flapping when a GPU costs this much
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prometheus:9090
      query: |
        sum(vllm:num_requests_waiting) /
        clamp_min(sum(vllm:num_requests_running), 1)
      threshold: "2"   # scale when waiting ≈ 2× running capacity pressure

Tune the threshold from load tests, not intuition. Pair KEDA (replica count) with a smart router (least-loaded / KV-aware routing) — scaling without good routing just creates more unevenly loaded pods.

🧪 Interactive: queue vs. replicas — feel Little's Law

Little's Law: L = λ × W — queue length = arrival rate × time in system. If arrivals exceed service capacity, the queue doesn't stabilize, it grows without bound. Drag arrival rate past capacity and watch.

Rule of thumb: keep ρ below ~0.7 for latency-sensitive serving. Queueing delay explodes as ρ → 1 — at ρ=0.9 average wait is ~9× service time; at ρ=0.99 it's ~99×. Headroom is the latency budget.

Cold starts: anatomy & mitigation

A cold start isn't one delay — it's a pipeline of delays, and for LLMs the model, not the container, is most of it.

1 · ProvisionCloud creates / schedules the GPU node. Spot or scarce GPUs can wait minutes or fail outright.5–120s+
2 · Image pullCUDA + PyTorch + server image is often 10–20 GB. Cached node = seconds; cold node = minutes.10–90s
3 · Model loadWeights from disk / object store → CPU RAM → GPU HBM. A 70B in FP16 is ~140 GB to move.20–120s
4 · Engine initCUDA graphs capture, KV-cache allocation, tokenizer, compilation (torch.compile / Triton).10–60s
5 · WarmupDummy requests so the first real user doesn't pay JIT / graph / cache warm-up.2–15s

Ranges are illustrative per-stage extremes — they don't sum to the typical total because stages overlap (e.g. image pull while node provisions) and best cases rarely stack. Typical measured totals land around 60–180s. Measure your own stack with timestamps at each stage.

Cheapest

Keep a warm floor

minReplicaCount: 1–2. Costs money 24/7, but removes cold start from the common path. Right answer for steady, SLO-bound traffic.

Predictive

Scale before the burst

Cron / forecast-based KEDA triggers for known peaks (9am, product launch). Scaling on schedule beats scaling on pain.

Technical

Shrink the load itself

Smaller / quantized weights, fast local NVMe or streamed loading, pre-pulled images on node pools, lazy CUDA-graph capture, snapshot/restore where supported.

Scale-to-zero is a pricing feature, not an SLO feature. It's excellent for dev, batch, and spiky internal tools. For user-facing chat, the first request after idle pays the full cold start — say that out loud in design review before choosing it.

Spot GPUs: cheap, until they're gone

Spot / preemptible GPUs are spare cloud capacity sold at a steep discount — reclaimable on short notice (often ~30s–2 min warning, provider-dependent). Design for interruption; don't hope it won't happen.

WorkloadSpot fitWhy
Batch inference, embeddings, evalsExcellentIdempotent, retryable, checkpointable; throughput matters, per-request latency doesn't.
Offline fine-tuning with checkpointingGoodResume from checkpoint; save often enough that lost work < checkpoint cost.
Dev / staging, load testsGoodInterruption is an inconvenience, not an incident.
Latency-SLO chat (sole capacity)PoorA reclaim during peak = queue spike + cold starts on replacement capacity simultaneously.
Chat with on-demand fallback fleetViable hybridSpot carries base load; router drains to on-demand on interruption signal. Complexity is the cost.

Interruption survival checklist

  • Listen for the termination notice; stop accepting new requests immediately (drain, don't drop).
  • Make requests idempotent / retryable at the router with a deadline budget.
  • Diversify: multiple instance types & zones — one pool reclaiming shouldn't take the fleet.
  • Keep the on-demand floor sized for your SLO, not for average load.

The real spot equation

Effective saving = discount − (wasted partial work + re-queue latency + fallback premium + engineering complexity). If interruptions hit 10% of capacity-hours at peak, a headline “70% off” can net far less. Measure cost per completed token on spot, not the sticker price.

Cost per token: the unit that runs the business

Every pricing page, capacity plan, and model-choice argument reduces to this. Derive it, don't quote it.

cost per 1M output tokens = (GPU $/hr ÷ 3600) ÷ (tokens/sec × utilization) × 1,000,000

Worked example

One H100 at $3.00/hr (illustrative), serving at 1,200 tok/s aggregate decode throughput, at 50% realized utilization:

  • Effective throughput = 1,200 × 0.50 = 600 tok/s
  • Tokens per hour = 600 × 3,600 = 2.16M
  • Cost per 1M tokens = $3.00 ÷ 2.16 = $1.39
  • At 25% utilization it doubles to $2.78. Utilization is the price.

Input/prefill tokens, idle time, non-GPU costs (CPU, storage, egress, observability) and failed requests all belong in a full accounting — this formula is the floor.

MFU: how much of the GPU are you actually using?

Model FLOPs Utilization = observed FLOPs/sec ÷ peak hardware FLOPs/sec. It's the standard yardstick for training efficiency — and a useful, but easily misread, lens for inference.

MFU = (6 × N_params × tokens/sec) ÷ peak_FLOPs  ·  [training approx: forward+backward ≈ 6 FLOPs / param / token]

Reading MFU honestly

  • Training: 40–55% is strong for large dense models; communication, memory stalls, and small per-device batches eat the rest.
  • Inference prefill: compute-bound, can reach respectable MFU at large batch.
  • Inference decode: one token at a time per sequence, dominated by reading weights from HBM — MFU is inherently low. Low decode MFU ≠ badly tuned; check memory bandwidth utilization and tokens/sec instead.
  • MFU ignores data type: quote it with precision (BF16 vs FP8 peaks differ ~2×).

Goodput > utilization

The metric executives should ask for is goodput: tokens (or requests) completed within SLO per dollar. A fleet at 95% utilization with p99 TTFT blowing the SLO has worse goodput than one at 65% that meets every deadline. Optimize goodput; report utilization as a diagnostic, never as the goal.

Check yourself

Traffic doubles in 60 seconds. KEDA is configured perfectly. Why do users still see timeouts?

Because replica creation isn't capacity — the new GPU must provision, pull, load the model, and warm up (often 60–180s+). During that window the existing fleet absorbs 2× load, queues grow super-linearly (ρ→1), and timeouts cascade. Mitigations: warm floor, predictive scaling, request shedding / admission control, and a router that protects in-flight work.

Spot is 70% cheaper. Your batch job's cost only fell 30%. Where did the rest go?

Interruptions waste partial work, checkpoints cost time and storage, replacement capacity may come up at worse prices or not at all, and retries duplicate compute. Measure cost per completed job — sticker discount minus waste is the real discount.

Decode MFU is 4%. Is the serving stack broken?

Probably not. Decode is memory-bandwidth-bound: each token requires streaming the model's weights from HBM, so FLOPs sit idle waiting on memory. Judge decode by tokens/sec, memory-bandwidth utilization, and goodput — and raise effective throughput with continuous batching so weight reads are amortized across many sequences.

Production checklist — Stage 10 sign-off

  • Autoscaling signal is queue / KV pressure, not CPU
  • Cooldown & warm floor sized from measured cold-start time
  • Cost per 1M tokens computed from measured throughput × utilization
  • Spot used only where interruption is designed for, with an on-demand floor for SLO traffic
  • Dashboard shows goodput (within-SLO tokens/$), queue depth, TTFT p95, and MFU/bandwidth together
