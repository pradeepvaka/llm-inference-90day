The AI gateway: one front door

An AI gateway is a proxy that sits between every client and every model deployment — hosted APIs and your own fleets alike. It presents one API (usually OpenAI-compatible), one auth model, and one place where policy lives. Products in this space: LiteLLM, Portkey, Kong AI Gateway, Cloudflare AI Gateway, OpenRouter — and a thin in-house proxy is a legitimate choice at small scale.

What the gateway owns

  • Authentication & virtual keys — one key per team/app, revocable, never a raw provider key in client code.
  • Routing — which deployment serves this request (§2).
  • Rate limiting & quotas — per key, per tenant, per model (§4).
  • Fallback & retries — the chain in §3, executed in one place.
  • Cost accounting — tokens × price, attributed per key, in near-real time.
  • Observability — every request logged/traced with the same schema (§6).
  • Guardrails hooks — PII redaction, prompt filters, output checks (keep them cheap and async where possible).

What it must never own

  • The inference itself. The gateway adds a network hop and policy checks — budget it: a well-run gateway adds ~1–5 ms, not 50 ms of JSON gymnastics.
  • Business logic. Prompt construction, conversation state, and tool orchestration belong to the app. A gateway that knows your prompts becomes a monolith nobody can deploy.
  • Silent quality changes. If a fallback swaps models, that fact goes in the response metadata and the logs — users and evals must be able to see it.
  • A single point of failure. The gateway is now on the critical path: run it replicated, stateless, with its config cached locally so a config-store outage doesn't become an inference outage.

A gateway config with routing, fallback, and limits (LiteLLM-style YAML)

# One logical model name, three real deployments behind it

    litellm_params: { model: openai/gpt-4o,        api_key: os.environ/OPENAI_KEY }

  - model_name: chat-prod
    litellm_params: { model: anthropic/claude-sonnet-4-5, api_key: os.environ/ANTHROPIC_KEY }
    model_info:     { id: anthropic-secondary, cost_per_1k_out: 0.015 }
  - model_name: chat-prod
    litellm_params: { model: hosted_vllm/llama-3.3-70b, api_base: http://fleet.internal:8000 }
    model_info:     { id: selfhost-fallback, cost_per_1k_out: 0.0014 }  # your Stage-10 number

router_settings:
  routing_strategy: latency-based-routing   # §2
  num_retries: 1                               # per deployment, then fall over (§3)
  timeout: 30                                  # seconds, whole request — sized from the SLO (§5)
  fallbacks: [{ chat-prod: [chat-prod] }]     # same group = try next deployment
  allowed_fails: 3                               # circuit breaker: 3 fails → cool down this deployment
  cooldown_time: 60                             # seconds out of rotation

general_settings:
  master_key: os.environ/GATEWAY_MASTER_KEY
  # Per-key limits are set on virtual keys, not here (§4)

Exact key spellings vary by gateway and version — check your gateway's docs. The shape is the lesson: one logical name, N deployments, policy stated once, in config, where it can be reviewed and rolled back like code.

Routing: picking the deployment per request

Routing decides, for each request, which backend gets it. The right strategy depends on what varies between your backends: load, cache state, capability, or price.

StrategyHow it decidesUse it whenWatch out
Round-robin / weightedRotate, or split by fixed weightsHomogeneous replicas of the same modelBlind to load — one slow replica still gets its full share
Least-loadedFewest in-flight requests / shallowest queueSelf-hosted fleets with uneven request costsNeeds fresh load signals; stale metrics herd everyone to the same “empty” node
Latency-basedRecent TTFT / end-to-end latency per deploymentMultiple providers with variable performanceCan starve a recovering backend of the traffic it needs to look healthy again

Worked math: what a cascade saves

Suppose 1M requests/day. A difficulty classifier sends 70% to a small model at $0.20 / 1M tokens and 30% to a frontier model at $5.00 / 1M tokens, averaging 800 total tokens per request:

  • All-frontier: 1M × 800 × $5.00/1M = $4,000/day
  • Cascaded: (0.7 × 800M × $0.20/1M) + (0.3 × 800M × $5.00/1M) = $112 + $1,200 = $1,312/day
  • Saving ≈ 67% — if the classifier's false-easy rate stays low. At a 5% false-easy rate, 35,000 requests/day silently get the weak model. Price the eval harness that watches that number; it is part of the routing cost.

Routing is a per-request decision, fallback is a per-failure one

Keep the two separate in your head and your config:

  • Routing runs before the request: pick the best deployment given load, cache, cost, capability.
  • Fallback runs after a failure or deadline miss: pick the next acceptable deployment (§3).
  • Conflating them produces the classic bug: a “router” that only discovers a backend is down by sending it production traffic.
  • Health signals feed both: routing avoids the loaded, fallback avoids the dead.
3

Fallback chains: reliability you can compute

A fallback chain is an ordered list of deployments the gateway tries until one succeeds or the request's deadline dies. Four mechanisms do the work — retries, timeouts, circuit breakers, and the chain itself — and each one can hurt if tuned by vibes.

Attempt 1

Primary deployment. Full timeout budget minus a reserve (e.g. 70% of the request deadline). Most requests end here.

Attempt 2

Same model, different provider/region if you have it — quality identical, failure domain different. Triggered by 5xx, timeout, or circuit-breaker-open, not by a 400 (your request is wrong everywhere).

Attempt 3

Degraded-but-alive: a different model family, or your self-hosted fleet. Log the substitution, tag the response, and let product decide which features degrade (shorter max_tokens, no tools) rather than failing outright.

Terminal

Fail honestly: a fast, well-formed error with a Retry-After, or a queued/async acceptance for batch-class traffic. A clear 503 in 200 ms beats a 30 s hang that ends in a timeout the client retries anyway.

Chain availability (independent failures) = 1 − Π (1 − Ai)  ·  three deployments at 99% each → 1 − 0.01³ = 99.9999%

Why the formula lies (a little)

  • Failures correlate. Two “independent” providers may share a cloud region, a DNS provider, or your own gateway's egress. Common-mode failure eats the theoretical nines.
  • Fallback capacity is finite. If the primary carries 80% of traffic and dies, the secondary inherits 5× its normal load — and may fall over too (a cascading failure). Load-test the chain at full failover volume, not at failover trickle.
  • Latency multiplies. Availability counts a 29-second success as success. Your SLO (§5) may not. Track within-SLO success, not raw success.
  • Realistic outcome for a well-built 2–3 provider chain: ~99.9–99.95% end-to-end — a genuine, worthwhile improvement over a single 99% provider, just not six nines.

Retries: the amplifier you tune

  • Retry load math: with per-attempt failure rate f and up to r retries, expected attempts = 1 + f + f² + … ≈ 1/(1−f). At f = 0.3 that's 1.43× load on a backend that is already failing — retries during an outage are a self-inflicted DDoS.
  • Only retry what's safe: timeouts and 5xx/429-with-backoff; never a 4xx validation error. Streaming requests that already emitted tokens generally can't be retried transparently — the client has half an answer.
  • Exponential backoff + full jitter: sleep = random(0, min(cap, base × 2attempt)). Jitter is what stops 10,000 clients from retrying in lockstep.
  • Retry budget: cap retries globally (e.g. retries ≤ 10% of requests per minute, token-bucket enforced). When the budget is spent, fail fast — the budget is what keeps a bad deploy from becoming an outage.

Circuit breakers: stop asking the dead

After N consecutive failures (or a failure-rate threshold over a window), the breaker opens: the gateway skips that deployment instantly instead of paying a timeout per request. After a cooldown (30–60 s typical), it goes half-open: a few probe requests decide whether the deployment rejoins rotation. Without a breaker, a dead primary adds its full timeout to every request before fallback even starts — at a 10 s timeout, your p95 just became 10 s.

Timeouts are a budget, not a setting

Work backwards from the SLO. If the end-to-end budget is 30 s and a fallback attempt needs ~8 s to be useful, the primary gets at most ~20 s — and the client-facing deadline must be enforced by the gateway, not hoped for. Split budgets per attempt, shrink them as the deadline approaches, and never let attempt timeouts sum past the request deadline. Also set a separate, shorter TTFT timeout: no first token in X seconds usually means no answer is coming — fail over while there's still budget to succeed elsewhere.

4

Rate limits: backpressure with good manners

LLM rate limits come in two currencies — requests and tokens — and a request only proceeds if it can pay both. Limits exist at three layers: the provider's (imposed on you), the gateway's per-key quotas (imposed by you), and your fleet's physical capacity (imposed by physics).

RPM, TPM, and why tokens win

  • RPM (requests/min) is easy to count and nearly meaningless alone: a 10-token request and a 100k-token request are both “1”.
  • TPM (tokens/min) tracks real work — but which tokens? Providers differ: some count input + output, some count input + max_tokens reserved up front. Read the fine print before sizing against a tier.
  • Concurrency limits are the third rail for self-hosted fleets: your binding constraint is KV-cache / batch slots (Stage 4), not a per-minute counter.
  • Production gateways enforce all applicable limits at once and return 429 with Retry-After and a header naming the limit that fired.

Token bucket: the math underneath

A token bucket refills at rate r up to capacity B. A request costing c tokens proceeds if the bucket holds ≥ c.

  • Sustained rate = r. Burst allowance = B. A 1M TPM limit as a bucket: r = 16,667 tok/s; with B = 250k, a tenant can burst 250k tokens instantly, then is throttled to the refill rate.
  • Sizing B is a fairness decision: B too large lets one tenant's burst starve others at minute boundaries; B too small rejects legitimate spiky-but-small tenants.
  • Estimate-then-reconcile: prefill cost is unknown until tokenized, output cost unknown until generated. Gateways reserve an estimate (prompt tokens + max_tokens) at admission and settle the actual count at completion.

Worked example: sizing a tenant quota

A tenant's traffic: 120 RPM average, prompts of 2,000 input tokens, 500 output tokens per response, peak-to-average ratio 2.5×.

  • Average TPM = 120 × 2,500 = 300k tokens/min
  • Peak TPM = 300k × 2.5 = 750k tokens/min — set the quota here, not at the average, or the tenant gets 429s exactly at their busiest (and most valuable) moments.
  • Provider-side cost of that peak: if your upstream tier is 10M TPM shared across 20 such tenants, aggregate worst case is 15M TPM — oversubscribed 1.5×. That's fine if peaks don't correlate; it's an incident if they all peak at 9 AM. Know which world you're in (§6 dashboards will tell you).
  • Per-key gateway quota: TPM 750k, RPM 400 (peak requests with headroom), concurrency 64. Breach behavior: queue briefly at the gateway (bounded, e.g. 2 s) before returning 429 — a small queue absorbs micro-bursts cheaper than clients retrying.
429 is a routing signal. When a provider returns 429, the gateway should mark that deployment rate-limited (distinct from down), shift new requests to other deployments, and retry within the same provider only after Retry-After. Treating 429 as a generic error causes retry storms against a provider that is explicitly asking you to slow down.

TTFT & ITL SLOs: two budgets, one promise

A streamed response spends its latency in two different physics regimes. Time to first token (TTFT) is dominated by queueing + prefill: compute-bound, scales with prompt length. Inter-token latency (ITL) is decode: memory-bandwidth-bound, scales with batch size and model size. One blended “latency” number hides which regime is hurting — so SLO them separately.

End-to-end latency ≈ queue wait + TTFT + (output tokens − 1) × ITL  ·  a 500-token answer at ITL 40 ms spends ~20 s generating — TTFT is not the whole story

ITL p95< 50 ms/token (≈ 20 tok/s per user — faster than reading speed)Batch size, model size, KV pressure on the replicaOversized batches chosen for throughput; prefill chunks interrupting decode (mitigate with chunked prefill, Stage 5)
End-to-end p99Per request class — must be stated with an output-length assumptionBoth of the above + fallback attemptsUnbounded output lengths; fallback timeout stacking (§3)

Error budgets: turning the SLO into a decision rule

  • A 99.9% monthly availability SLO leaves an error budget of 0.1% ≈ 43 minutes of full outage equivalent per 30-day month — or, counted in requests, 1,000 failed requests per 1M.
  • Burn rate = observed error rate ÷ budget rate. Burn rate 1 consumes the budget exactly on schedule; burn rate 10 consumes it in ~3 days.
  • Alert on burn rate, not raw errors: page at burn ≥ 14.4 over 1 h (2% of monthly budget in an hour), ticket at burn ≥ 3 over 24 h. This is the multi-window burn-rate alerting pattern from the Google SRE workbook.
  • Budget spent? Freeze risky changes, keep reliability work. Budget healthy? Ship. The budget — not an argument in a meeting — arbitrates velocity vs. stability.

Observability: prove it, per request

The gateway is the one place every request passes through — which makes it the one place that can tell the whole truth: which deployment served, what it cost, how long each phase took, and whether the answer came from the primary or the third fallback.

Metrics

Histograms, not averages

  • ttft_seconds and itl_seconds as histograms, labeled by model + deployment — averages hide exactly the tail your SLO lives in.
  • Counters: requests by status class, fallbacks attempted, circuit-breaker state changes, 429s by limit type.
  • Gauges: in-flight requests and queue depth per deployment (the signals §2 routing consumes).
  • Tokens in/out per key → cost per key, computed at the gateway.
Traces

One trace per request

  • Spans: gateway admission → route decision → attempt 1 → (fallback) attempt 2 → stream. The trace is the fallback chain's receipt.
  • Propagate a request ID end-to-end: client → gateway → provider call → logs. Every support question starts with “what happened to request X?”
  • Sample smartly: keep 100% of errors and fallbacks, sample successes (e.g. 5%) — full tracing of every streamed token is a cost center, not a feature.
Logs

Structured, and careful

  • One structured record per request: key ID, model requested vs. model actually served, tokens, latency split, status, cost.
  • Prompt/response content logging is a privacy decision, not a debugging convenience: off by default, redacted when on, retention stated.
  • Log the route decision's reason (least-loaded, breaker-open skip, cache affinity) — “why did it go there?” is the second support question.

# TTFT p95 per deployment, 5-minute window

The gateway dashboard (one screen, in order)

  • Top: SLO panels — TTFT p95, ITL p95, within-deadline success %, current burn rate. Red here means users hurt now.
  • Middle: traffic & routing — requests by deployment, fallback rate, breaker states, 429 rate by limit.
  • Bottom: economics — tokens and $ by tenant/model, cache hit rate, cost per 1M tokens vs. Stage-10 baseline.
  • If the on-call has to open a second dashboard to explain the first one, the first one is decoration.

Alert on symptoms, not causes

  • Page: burn-rate breaches, within-SLO success dropping, all deployments of a model down. These are user pain.
  • Ticket: one deployment's error rate rising, cache hit rate decaying, cost-per-token drift. These are tomorrow's pages.
  • Never page on a single provider's status page alone — your own measurements are the source of truth, and the fallback chain may already be handling it (in which case you want a ticket, sleep, and a postmortem action item — in that order).

Chaos testing: rehearse the bad day

Every mechanism in this stage — fallback, breakers, budgets, alerts — is a hypothesis until you've broken production-shaped traffic on purpose. Chaos testing for inference gateways means injecting provider-shaped failures, not just killing pods.

Run experiments under a load generator replaying production-shaped traffic (Stage 12's benchmark rig is perfect for this), or the green results won't survive contact with a real outage.

Lab C — Game day

Pick three rows from the §7 experiment table. Write the hypothesis for each before injecting anything.

  • Run under replayed production-shaped load

  • Deliverable: a one-page game-day report — hypothesis, result, fix, re-run date

Check yourself

Your chain has three providers at 99%, 99%, and 98%. A teammate claims 99.99998% availability. What's wrong with the claim — and what's still true?

The arithmetic (1 − 0.01×0.01×0.02) assumes independent failures and infinite fallback capacity. Shared regions, shared egress, failover overload, and rate-limit ceilings correlate real failures, so the honest expectation is closer to 99.9–99.95%. What's still true: the chain is 10–50× better than the single best provider alone (99% → ~43 hours/month of downtime budget vs. ~22–44 minutes). The direction is right; the precision is fiction.

The primary provider is returning 429s. Your gateway retries each request 3 times with no delay. What happens next, and what's the fix?

Request volume to the limited provider roughly triples-to-quadruples, the 429 rate climbs, and the retries consume the request deadline so fallback starts too late. Fix: treat 429 as a routing signal — mark the deployment rate-limited, shift new requests to other deployments immediately, honor Retry-After for any same-provider retry, and enforce a global retry budget.

TTFT p95 is comfortably under SLO but users complain answers “feel slow.” Where do you look?

ITL and total completion time. TTFT only measures the wait for token one; a 600-token answer at ITL 90 ms takes ~54 s to finish. Check ITL p95 (batch size / replica load), the output-length distribution (a few very long generations dominate perception), and whether prefill chunks from other requests are stalling decode on shared replicas.

During a game day, failover works perfectly at 200 requests/min. Production peak is 2,000. What did the experiment actually prove?

That the mechanism works — breaker, routing, config — at low volume. It proved nothing about failover capacity: secondary TPM tiers, connection limits, and queue behavior at 10× load are untested. Either re-run under replayed peak-shaped load or record the capacity question as an open risk with an owner. A game-day report that doesn't state the load it ran at is incomplete.

Production checklist — Stage 11 sign-off

  • One logical model name per capability; provider keys exist only in the gateway, never in client code
  • Fallback chain tested at full failover volume, including the secondary's TPM tier
  • Per-attempt timeouts derived from the end-to-end budget, with a separate TTFT deadline
  • Retries: idempotent-safe failures only, exponential backoff + full jitter, global retry budget enforced
  • 429 handled as backpressure/routing signal, with per-key RPM + TPM + concurrency quotas
  • TTFT and ITL SLOs stated with percentile, prompt/output-length classes, and a burn-rate alert
  • Every request traceable: route decision, deployment actually served, tokens, cost, latency split
  • At least one game day run under realistic load, with findings fixed and re-tested
